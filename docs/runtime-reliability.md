# 插件与管理面板故障保护

这些保护用于让常见插件故障不再持续占用整个服务。它们不是恶意代码沙箱，也不是所有操作系统故障的兜底。

## 执行和等待限制

- JS/Lua 每次进入运行时默认有 **5 秒**执行预算。嵌套调用、JS Promise 队列和受控 HTTP 请求共享预算，不能通过反复调用延长时限。
- 骰主可以在 `config/dice.json` 设置 `plugin_timeout_ms`，范围 100～60000 毫秒，重启后生效。确实需要较长外部请求的可信插件可适当调高；提高时限也会增加一次故障的等待时间。
- 同一个运行时忙碌时，其他调用最多等待 **100 毫秒**，之后返回忙碌错误；没有命中插件的管理接口仍可使用。现有接口可能以业务错误返回，未捕获的运行时忙碌异常以 HTTP 503 和 `Retry-After` 返回。
- JS/Lua 单个运行时的脚本分配默认限制为 **256 MiB**。Lua 只在受保护执行中拒绝超限分配，避免宿主准备调用栈时触发 Lua panic；这不是整个进程的严格内存配额。
- 单个 JS/TS/Lua 源文件最多 **4 MiB**；超限不执行。JS 管理列表保留超限文件及原因。大型插件应拆分模块；此限制不等于压缩包上传大小限制。

## 超时之后

超时的 JS 插件/Lua 模组在当前运行时内暂停，避免每条消息都重复进入死循环。管理列表显示恢复提示，文件不改名、不删除；修复或禁用问题文件后，重载可重新启用。重载整批插件也受预算约束，后续插件可能没有完整加载，应先处理日志中第一个超时文件，再重载检查。

重复 JS 定时器抛错或超时后停止重排；Promise 队列超时后暂停到重载，避免残余任务反复占用服务。Lua 的 `sleepTime` 正常挂起保留原有行为，最多同时保留 256 个等待中的回复；执行超时不再误判成等待并继续重排。

JS 定时器、WebSocket 事件和 Lua 延迟回调交给独立后台工作线程，不在主 I/O 循环上运行脚本。每种语言最多排队 128 个回调；满队列时拒绝并记录警告。退出时丢弃待执行回调、等待当前受控调用结束，再关闭数据库。

## Lua 原生功能的变化

- `debug.sethook` 不再允许覆盖宿主时限钩子。
- `os.exit` 不允许插件关闭整个骰子；退出使用管理面板或托盘。
- `os.execute` 和读取模式 `io.popen` 使用可取消的子进程树。`io.popen` 是有界输出快照，支持通常的 `read/lines/close`，最多 2 MiB；不再支持写入模式 `w` 或持续交互管道。
- 通过 `setmetatable` 注册的 Lua `__gc` 清理函数使用受控协程执行，防止正常垃圾回收、删除或退出被循环清理函数拖住。返回值不是进程隔离；刻意修改元表、读取原始 C 函数或调用原生库不能视为安全。

## 其他故障点

用户提供的高级回复、因果回复和 Lua 正则匹配使用独立的 ECMAScript 引擎；单次最多 100 毫秒，超时表达式在当前线程暂停。原有前缀、全文、搜索和捕获组语义保留；现在遵循 JS 字符串/正则的 Unicode 语义，不再依赖各平台 `std::regex` 的字节实现。

首页只读取最新日志文件末尾 512 KiB，避免反复扫描一天的大日志。心跳、云黑和历史图片后台处理补充异常边界，错误记录到日志，不再因这些路径中的未捕获异常直接终止进程。

## 验证与边界

`node tools/test-plugin-reload.mjs <core-binary> [lua-file] --reliability` 使用临时数据与回环监听，验证真实服务的插件死循环、加载超时、协程续跑、并发 API、删除恢复和执行中的退出。不连接机器人或外部服务。

原生 DLL/动态库、插件自行取得的未受控函数、阻塞文件设备、操作系统/磁盘故障、原生崩溃，以及部分仍使用分离线程的服务生命周期，不受脚本钩子完整隔离。要进一步覆盖这些情况，需要独立插件进程、IPC 超时和明确的资源/权限边界；本轮不声称已实现。Windows Job Object 分支需要 Windows CI 与实机验收，POSIX 本地测试不能替代它。
