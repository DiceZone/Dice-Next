## 发布前的发行包验收

分别在 Linux amd64/arm64 与 macOS arm64 使用独立测试实例，记录源/目标包、操作系统、架构、启动方式、安装目录、原配置参数与结果。

1. 完整解压含管理器的新包，通过 `start.sh` 启动；再测试 systemd/launchd 的前台托管。自定义配置目录使用绝对路径。
2. 从面板下载并手动安装实际新版本；确认版本/构建号、WebUI、语言、内置资源和 Linux 动态库同步更新。确认管理器与核心均换成新版本。
3. 检查配置、数据库、进行中的日志、用户牌堆、非内置插件与自定义配置目录未被覆盖。升级前保留独立备份。
4. 逐项验证通知/下载/立即安装/定时安装，服务器时区与跨日时间，计划持久化；仅下载不在下一次启动时擅自安装。
5. 测试下载取消、损坏 tar、穿越/PAX 路径、逃逸符号链接、错误架构、缺失动态库及目录不可写。失败不得覆盖旧核心或留下自动重复安装循环。
6. 在无真实数据的测试目录中模拟替换中断，检查下次管理器启动能够恢复程序文件；保留事务和回滚目录。程序成功加载后的业务错误、数据库迁移不自动降级。
7. 普通重启保留完整参数；管理器完全等待旧核心退出，服务监控不应拉起第二套实例。杀死管理器而核心仍存活时，第二管理器不得替换文件。
8. macOS 保留 Gatekeeper/隔离属性正常工作，不以删除安全属性或自动提权冒充更新成功。
9. Docker/Podman 仍拒绝自更新，只检查通知。旧 beta.928 安装需先手动覆盖到新管理器包一次；直接运行核心不显示安装能力。

自动化入口：`dice-next-tests` 的 UpdateSchedule/PosixUpdate/PosixArchive；`node tools/test-posix-manager.mjs <dice-next> <dice-next-update-test-core>`。后者是轻量发布门禁，不替代上述发行包验收。

`Cross-platform update checks` 为分支验证工作流：Linux amd64/arm64 与 macOS arm64 编译真实核心、管理器、测试并打包，校验包内核心和管理器的加载能力；Windows amd64 检查共享更新逻辑回归。自动使用三个仓库的 `cross-platform-update` 分支，复用原依赖缓存，不发布 Release、修改主分支或推送构建号。验证包只保留为 Actions artifacts，不视为正式版本。
